# Phase 5 — 워치 컴패니언 (Galaxy Watch / Wear OS)

> 상태: **준비(PRD)** · 미착수 · 작성 2026-07-27
> 선행: Phase 1–4 완료(편성·배정·배차 F5·투어 F6). 백엔드 API 재사용이 전제.

## 0. 목표 (Goal)
수양회 참가자가 **손목에서 즉시 확인·행동**할 수 있는 얇은 컴패니언 앱.
전체 앱을 이식하지 않는다 — 폰 앱은 그대로 두고, 워치는 **글랜스(조회) + 알림 + 즉시 동작(SOS)**만 담당한다.

## 1. 배경 · 원칙
- Mana 폰 앱은 8단계 등록·대시보드·배차판 등 **큰 화면·입력 중심** → 원형 ~450px 워치에 부적합.
- 반대로 **"내 다음 일정 / 내 픽업 차편 / 내 방·조 / SOS"**는 손목에 최적.
- 백엔드(FCM·schedules·transport·assignments·sos)는 **이미 존재** → 워치는 조회+알림 클라이언트.
- **폰 페어링 전제**: 워치 단독 로그인(google_sign_in) 지양 → 토큰은 폰에서 핸드오프.

## 2. 플랫폼 결정
| 기기 | OS | 방침 |
|---|---|---|
| Galaxy Watch 4·5·6·7·Ultra | **Wear OS**(Android 기반) | **지원 대상**. Flutter Android 툴체인·코드 재사용 |
| Galaxy Watch 3·Active2 이하 | Tizen | **범위 외**(flutter-tizen 별도 툴체인, 추후 검토) |

> Flutter의 Wear OS 지원은 비공식(커뮤니티 `wear` 패키지)이나 실사용 가능. 리스크는 §7.

## 3. 범위 (Scope)
### In
- W0 알림 미러링(프로그램·SOS·픽업 변경 알림을 손목에서 읽기 좋게)
- W1 내 다음 일정(장소+내용)
- W2 내 픽업 차편(차량·시각·집결지·기사)
- W3 내 방·내 조
- W4 SOS 손목 버튼(위치 포함)
### Out (이번 단계 제외)
- 등록/수정, 관리자 대시보드·배차판·수납, 투어 갤러리, Tizen, 워치 단독 로그인, 오프라인 캐시 고도화

## 4. 화면 (글랜스 카드)
스와이프로 넘기는 카드형 UI. 각 카드는 단일 목적·2~3줄 정보.

| ID | 카드 | 표시 내용 | 소스 API |
|---|---|---|---|
| W1 | 다음 일정 | HH:mm · 제목 · 장소 | `GET /schedules/:programId` |
| W2 | 내 픽업 | 방향·차량·출발시각·집결지·기사 | `GET /transport/:id/my-transport` |
| W3 | 내 방·조 | 방 이름/층 · 말씀조 이름 | `GET /assignments/:id/rooms`·`/groups`(내 것 필터) 또는 신규 `my-*` 요약 |
| W4 | SOS | 큰 버튼 → 위치와 함께 발신, 확인 다이얼로그 | `POST /sos` (+ `geolocator`) |

> 랜딩 카드는 W1(다음 일정) 권장. 앰비언트 모드에서는 W1 요약만 저전력 표시.

## 5. 재사용 매핑 (신규 최소화)
| 자산 | 재사용/신규 |
|---|---|
| `ApiClient`(http·토큰 헤더) | **재사용** — 워치 타깃에서 그대로 import |
| FCM 알림(`fcm.js` + cron) | **재사용** — Wear OS가 폰 알림 자동 미러링(개발 0). 본문만 손목 가독성으로 다듬기 |
| `my-transport`·`schedules`·`sos` 라우트 | **재사용** |
| 내 방/조 요약 | 소폭 신규 권장: `GET /assignments/:id/mine`(reg 기준 방·조 1건 반환) — 워치 페이로드 축소용 |
| 인증 토큰 | 신규: 폰→워치 핸드오프(§6) |

## 6. 인증 전략 (폰 페어링)
- MVP: 폰 앱이 로그인 후 JWT를 **Wear Data Layer(MessageClient/DataClient)** 로 워치에 전달 → 워치 `ApiClient`가 저장·사용.
- 대안(핸드오프 미구현 시): 워치에서 **기기 코드/QR 1회 페어링**(폰이 승인) — 추후.
- 워치에서 google_sign_in **미사용**.

## 7. 리스크
1. **Flutter Wear OS 비공식** — 라운드/앰비언트/타일·컴플리케이션 한계. 실기기 조기 검증 필수.
2. **google_sign_in 워치 부적합** → §6 핸드오프로 회피(핸드오프 구현 난이도가 최대 리스크).
3. **배터리/앰비언트** — 폴링 대신 알림 푸시 + 열었을 때만 조회.
4. **firebase_messaging on Wear OS** — 독립 FCM 토큰 필요 여부 검증(미러링만으로 충분한지). 미러링이면 개발 0.
5. **Tizen 구형 기기** 제외 — 사용자층에 구형 비중 크면 재검토.

## 8. 하위 단계 · 태스크
### Phase 5.0 — 알림 미러링 검증 (개발 ≈ 0) — 진행 중
- [x] FCM 일정 알림 문구를 손목 가독성으로 정리(행사명·"5분 후 시작" 앞쪽) — `index.js` cron
  - 참고: `program_schedules`에 장소 컬럼 없음 → 장소 표기는 F8(스키마 추가) 후 가능
- [ ] **실기기 검증(사용자)** — 아래 체크리스트
  1. Galaxy Watch(Wear OS)를 폰과 페어링, 폰에 Mana 설치·로그인(FCM 토큰 등록됨)
  2. 폰 시스템 설정에서 Mana 알림 허용 + 워치로 알림 미러링 ON(Galaxy Wearable → 앱 알림)
  3. 서버에서 임박 일정 생성(또는 테스트 알림) → **5분 전 알림이 손목에 뜨는지 확인**
  4. SOS 발령 시 관리자 폰→워치에 `🆘 SOS: 이름`이 뜨는지 확인
  5. 손목에서 제목/본문이 잘리지 않고 읽히는지(행사명이 먼저 보이는지) 확인
- 판단: 미러링만으로 충분하면 경로 A로 종료 가능. 부족하면 5.1 컴패니언 착수.

## 9. 결정 사항 (Decided 2026-07-27)
1. 대상 기기: **Wear OS만** (Galaxy Watch 4+). 구형 Tizen 제외.
2. 인증: **폰→워치 토큰 전달(Wear Data Layer)**. 워치 단독 로그인 없음.
3. 최소 스코프: **W1 일정 · W2 픽업 · W4 SOS 우선**. W3(방·조)는 후순위.
4. 이번 목표: **경로 A(알림 미러링)부터 검증** = Phase 5.0. 결과 보고 5.1(컴패니언) 진행 여부 결정.

## 10. 성공 기준
- 참가자가 폰을 꺼내지 않고 **다음 일정·내 픽업**을 손목에서 확인.
- **SOS를 손목에서** 위치와 함께 1탭 발신.
- 프로그램 시작 알림이 손목에 도달.
